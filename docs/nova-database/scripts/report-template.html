Three structural facts

01 / ONE HEADER, SEVERAL ROLES

OPS_HEADER stores orders, manifests, templates and quotes. Trigger source identifies PB_TYPE values O, M, T and Q.

02 / TWO STOP ROLES

OPS_MANIFEST_STOPS links a manifest routing stop to an order pickup/delivery stop. Both endpoints belong to OPS_STOP_REC.

03 / IDENTITY NEEDS CARE

Current driver IDs are joined to EQUIP_HEADER in Aurora. Driver-specific information also exists in DRIVER_HEADER; do not assume every driver field uses the same identifier.

Questions for a Nova owner

Which identifier does each driver field hold?

Confirm internal equipment IDs, driver detail IDs and legacy unit numbers before using fields beyond the explicit Aurora joins.

How do location discriminators work?

Fields such as OPS_LOC_TYPE + OPS_LOCATION and ES_LOC_TYPE + ES_LOCATION may resolve to different target tables. They are not mapped as unconditional location foreign keys.

Which relationships permit retained history?

OPS_HEADER_AFTER_DELETE explicitly preserves OPS_HISTORY for EDI delete/recreate behavior. Header-level history uses OPH_STOP_ID=0. A missing parent is not automatically corruption.

Can deleting a delivery stop leave a bridge reference?

OPS_STOP_REC_AFTER_DELETE deletes manifest links by OSM_STOP_ID, but does not explicitly clean OSM_PKUP_DELV_ID. Application cleanup may cover this; it was not established here.

How should legacy and composite references join?

PRO location/number/suffix, accounting-company keys, polymorphic insurance owners and tariff validity dates need business rules. Similar names alone are not enough to establish a safe join.
