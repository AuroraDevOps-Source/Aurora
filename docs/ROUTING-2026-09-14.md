# Routing analysis update

## Workflow

1. In **Delivery orders**, import or drop a PTV delivery-request JSON file (up to 25 MB). For a walkthrough, expand **More options** and choose **Load demo orders**. The same workspace shows fleet/order counts, the first five imported orders and their actual delivery/depot locations before optimization. This map is explicitly an input preview, not a calculated route; orders missing valid coordinates are flagged and remain in the input. Invalid replacement parsing preserves the previous draft.
2. Use **Edit fleet & limits** to adjust the fleet, earliest departure (ISO timestamp with offset), shift length, capacities, stop limits, costs and calculation budget before the first optimization. **Apply settings** updates the draft without submitting a job.
3. Expand **Appointments** to download the CSV template for the loaded PROs. Fill dated start/end timestamps and confirmation status, then import the CSV. Import is atomic: unknown/duplicate PROs, malformed rows, invalid times or conflicting windows reject the import without modifying the current scenario.
4. **More options → Download plan inputs** downloads the combined scenario, including reporting metadata; the original files remain unchanged. Drafts are not stored by this workspace.
5. Choose the main **Optimize routes** action. In results, use **Show on map** on a manifest, or the map's manifest selector. Select **All manifests** to restore all routes. Filtering does not submit a new optimization. Red unscheduled markers remain visible; overlapping orders share a counted marker. Fitting a selected route focuses its geometry, so distant red markers may be outside the current viewport.
6. Manifest rows display miles, duration and estimated cost. Expanded manifests display departure/return and stop arrival/departure alongside appointment windows. Schedule times use each vehicle's explicit earliest-departure offset, keeping the instant unchanged; if absent, the provider's offset is retained. Appointment times retain their source offset. Dates and offsets are visible; arrival may precede service because the vehicle can wait. An offset is not a named timezone and does not infer daylight-saving changes for multi-day planning.
7. Use **Export manifests** separately from **Export stops**, so repeated stop rows cannot accidentally be mistaken for separate manifest costs. The stop export includes appointment and schedule details. Raw request/response JSON and calculation diagnostics are under **More downloads**.
8. **Compare scenario** opens fleet settings for a new calculation against the current result. **New plan** clears the in-memory draft/result and returns to the empty planning workspace. Nothing is sent to dispatch automatically.

## Appointment input contract

CSV headers: `PRO,AppointmentStart,AppointmentEnd,AppointmentConfirmed`.
Accepted source aliases include `ProNumber` / `OrderId`, `BlockBegin`, `BlockEnd`, `Confirmed`, and `AppointmentDetail.BlockBegin`, `.BlockEnd`, `.Confirmed`.

Use ISO-8601 dates with `Z` or an explicit offset, e.g. `2030-01-01T09:00:00-06:00`. Do not use an undated time or guess the timezone from the machine. Confirmation accepts true/false, yes/no or 1/0. Blank template rows are ignored; a missing confirmation remains informational. PRO identifiers are matched exactly, preserving leading zeroes.

The JSON sidecar accepts keyed or array `reporting.orders`, with `appointment` or FreightOps `AppointmentDetail` objects. Their fields are `BlockBegin`, `BlockEnd` and `Confirmed` (case-insensitive). Other reporting fields are preserved.

Confirmed windows constrain the **start of service**, not necessarily the end of unloading. They are mapped to a cloned location's `stopProperties.timeSlots` and the delivery task's `timeSlotIds`, intersecting any existing allowed slots. Cloning isolates the order from other deliveries at the same address. Existing slot finish deadlines and other properties remain in force. Conflicting windows fail before calling PTV. Unconfirmed appointments are displayed but do not themselves add a constraint or exclude the order.

Native PTV time slots remain supported without imported appointment metadata. The root `reporting` sidecar is removed only after appointment constraints have been copied into the actual PTV request.

PTV references: [order task time slots](https://developer.myptv.com/en/documentation/route-optimization-optiflow-api/concepts/orders), [route appointments](https://developer.myptv.com/en/documentation/route-optimization-optiflow-api/concepts/routes). The DTO field names are also modeled in the existing Integration Hub `OptimizationRequestModels.cs`.

## Scope and limitations

- This remains a file-based delivery-analysis tool. It does not modify live shipments, issue notifications, book appointments or persist operational manifests.
- The meeting's original source-data extraction script has not yet been identified. This release supplies appointment import and a per-PRO template, not an unverified replacement for that extraction job.
- Pickup/load-balance modeling, multi-day driving rules, live-data selection, customer profiles, terminal networks and revenue balancing remain separate design work. The sample does not pretend to demonstrate these features.
- Costs are estimates from the optimizer and configured rates, not revenue or per-stop billing. Same-truck variation comparisons can contain different assigned orders and are labeled accordingly.
- The synthetic sample has two simultaneous appointments at separate locations, plus a third appointment before the available shift. No real customer data is included.
- Imported confirmed appointments require a fresh delivery request, not one containing preassigned routes, because the isolated location IDs would otherwise risk changing existing route restrictions. Native PTV windows without imported appointments remain unchanged.

`node tests/map-checks.mjs` exercises route filtering, restoration, persistent red markers, overlapping-order counts, escaping and map disposal using a Leaflet stub. Input-preview checks cover delivery/depot markers, coordinate validation/grouping, bounds, escaping and the absence of invented route lines. Routing checks also cover immutable draft parsing and preview metadata.
