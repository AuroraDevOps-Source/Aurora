# Dispatch

Dispatch is a separate step after accepting an optimization result and creating its Nova manifests. The Optimization UI, PTV requests, candidate selection, and manifest export are unchanged by this feature.

Open **Dispatch**, filter by manifest date, and double-click a manifest. Select a driver, review the truck, and choose **Save assignment** or **Dispatch manifest**. Dispatch also appears inside the existing Manifest detail screen. Missing assignments have the shared red data-requirement indicator in the dispatch grid.

Optimized manifests retain the accepted truck. Its identity is recovered from the existing tenant/draft/vehicle export reference; there are no changes to the export format. An old manifest referring to removed or renamed demo equipment cannot be dispatched with an arbitrary replacement. Replan using the current fleet. The preexisting WayTest manifests 11449 and 11450 refer to DEMO-MHT-20 and DEMO-MHT-11 respectively; neither exists in the current equipment list.

## Native records

- Statuses are looked up by `CT_STAT.CTS_CODE`: ASG for saved assignments and DPCH for dispatch. The manifest list includes DPCH even when its native manifest-visible flag is off.
- Assignments write `OPS_HEADER.PB_CURRENT_DRIVER` / `PB_CURRENT_TRACTOR` and one active, driver-keyed `DRIVER_PKUP_DELV` link. Drivers can be changed before dispatch.
- Release stamps manifest routing stops with dispatch time, driver, truck and dispatch status. Local delivery manifests also update linked delivery stops and order headers. `SET_ORDER_HDR_STATUS` is called explicitly because the stop-update trigger's SQL NULL comparisons miss first-time status changes.
- Line-haul release does not mark the consignee's final delivery stop as dispatched or delivered.
- Equipment status/history receives dispatch information. Nova's equipment trigger intentionally clears the transient current-manifest field after recording history; the header and driver assignment link remain authoritative.
- No departure/completion timestamps, route sequences, order memberships, accepted optimizer snapshots, or optimization settings are changed.
- The application log uses “Assigned manifest” and “Dispatched manifest.”

## Validation and transaction boundaries

Each operation is one Firebird transaction. It locks the manifest, then old/new resources in numeric order, then linked orders/stops. A revision covers the header, membership/order quantities, driver links, and execution state. Stale edits fail; a duplicate release with the same assignments is read-only and idempotent. Resources booked on another incomplete manifest for the same day, or on an explicitly active dispatched/in-transit manifest, are unavailable. Deleted equipment, wrong types, trucks at another terminal, insufficient capacities, empty manifests, changed/cancelled/delivered orders and mismatched optimized trucks are rejected. This is a conservative daily booking model; timed shifts or sequential routes on the same day are not scheduled here.

This first dispatch workflow supports native DRV drivers and TRK trucks. Tractor/trailer combinations and driver creation remain managed in Nova. In-progress or closed manifests are read-only here; driver messaging, departure/arrival, proof of delivery and completion workflows are separate work.
